**How the system determines a “session‑active” interval**

| Trigger                                              | What the engine does                                                                                                                                                                                                                                                                                                                                     | Resulting timestamp                                            |
| ------------------------------------------------------| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------| ----------------------------------------------------------------|
| **Heartbeat missing (network hiccup / player stop)** | 1️⃣ We look for the next *activity* event that returns to an “idle” state.  <br>2️⃣ If no such event occurs within the heartbeat‑timeout window (default ≈ 30 seconds in the production cluster) we automatically close the current active interval at `<last_heartbeat_time + timeout>`.                                                                    | `interval_end = last_known_good_timestamp + heartbeat_timeout` |
| **Player paused**                                    | The pause events are recorded as part of the session state stream (`session_state_paused`).  <br>The engine treats a *pause* like a temporary end to an active interval. When the user taps “play” again, a new active interval is opened with its own `interval_start`.                                                                                 | Two intervals: `…<‑pause_time>` and `<resume_time>‑…`          |
| **App backgrounded**                                 | Similar to pause: when the OS reports that the app has moved to the background (`session_state_background`), we treat this as an end to the active window.  <br>If the foreground event comes back within the *re-activate timeout* (again about 30 s default) a new interval starts immediately; otherwise the original session is considered finished. | `interval_end = background_time + re‑activate_timeout`         |

These rules are applied incrementally as events stream in, so by the time we persist data into **`session_active_intervals_clean`** each record has:

- **`video_session_id`** – the user‑session id that generated it  
- **`interval_start` / `interval_end`** – Unix epoch seconds of the activity window  
- **`platform`, `country`, etc.** – for slice‑by‑dimensional analysis
