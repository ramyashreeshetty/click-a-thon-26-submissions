# Architecture — AdVerdict (Team Dynamic Duo)

**One line:** ClickHouse computes every number; a fixed, deterministic query sequence
decides every drill-down; the LLM narrates and formats only; every step leaves a
queryable trace.

```
                 ClickHouse Cloud  (primary datastore + analytical engine)
  ┌────────────────────────────────────────────────────────────────────────┐
  │ dims + dictionaries ─▶ ad_events ──MV──▶ ad_events_enriched            │
  │        (attrs glued at insert)     └MV─▶ metrics_hourly_by_dim (rollup)│
  │ series_profile   incidents   investigation_steps   diagnoses           │
  └────────────────────────────────────────────────────────────────────────┘
        ▲ writes (rca_rw)                     ▲ read-only (librechat_ro)
  ┌─────┴─────────┐                    ┌──────┴────────┐      OTLP spans
  │    rca-mcp    │                    │ mcp-clickhouse│   ┌──────────────┐
  │ list_incidents│                    │  (official)   │──▶│  ClickStack  │
  │ investigate   │                    │ follow-up SQL │   │  (HyperDX)   │
  │ investigate_  │                    └──────┬────────┘   │ traces + dash│
  │   window      │                           │            └──────────────┘
  └─────┬─────────┘                           │
        └────────────► LIBRECHAT ◄────────────┘
          "what incidents?" → "why did fill drop?" → "which apps were hit?"
```

## Where the analysis executes — ClickHouse, not the LLM

- **Ingest**: one raw table; a materialized-view cascade glues dimension attributes
  on at insert (dictionaries) and maintains a long-format hourly rollup of **additive
  counters only** — every ratio is sum/sum at read, so any regrouping (hour → window →
  day) stays exact and alert numbers always reconcile with investigator numbers.
- **Detection**: per-series profiling (`seriesPeriodDetectFFT`, ACF, STL seasonal
  strength — measured, never assumed) selects each series' primary model; scoring runs
  a five-model ensemble (trailing median, hour-of-day, hour-of-week, STL, robust flat)
  **entirely in SQL** — window functions and `seriesDecomposeSTL`, robust sigmas
  (IQR/MAD) so an outlier can't inflate its own yardstick. Python only applies fixed
  gates (z ≥ 3 + practical significance from measured noise + volume floor),
  persistence, classification-by-model-disagreement, and dedup.
- **Attribution (the fixed q1–q6 sequence)**: q1 decomposes the revenue identity
  (requests × fill × render × eCPM) against same-weekday median baselines; q2 sweeps
  the moved lever's dimensions ranked by **contribution** (share-weighted delta, rollup
  fast-path); q3 re-sweeps with the candidate excluded — residuals collapsing to noise
  is the printed proof other dimensions were shadows; q5 (Kitagawa within/mix/
  interaction) gates GLOBAL verdicts against traffic-mix shifts; q4 peer-vs-sibling
  comparison covers history-free slices; q6 keeps baselines clean by excluding only
  **confirmed-cause** windows the system itself diagnosed earlier. The runner
  substitutes only whitelisted fragments into these fixed templates and compares
  returned numbers to fixed thresholds. **Zero SQL is generated by an LLM; zero
  verdicts are decided by one.**
- **Trust layer**: the narrator LLM receives a finished evidence bundle and writes
  prose. A mechanical guardrail then verifies **every figure in the narrative exists
  in the bundle** — a single unmatched number blocks publication and a deterministic
  template (built only from bundle values) publishes instead. The verdict, bundle,
  and `numbers_verified` flag are stored in `diagnoses`; every step's hypothesis,
  **exact SQL**, result rows, and decision stream live into `investigation_steps`.
  Ask the chat "how do you know?" and it shows you the trace.

## Integrations (each load-bearing)

- **LibreChat** — the product surface. An "RCA Analyst" agent with two MCP servers:
  `rca-mcp` (custom, ~90 lines: `list_incidents` / `investigate` /
  `investigate_window`) and the official `mcp-clickhouse` connected as a
  SELECT-only user for follow-up slicing, SQL always shown beside the answer.
- **ClickStack (HyperDX)** — ships in the compose stack and carries the whole trace
  story: investigation spans stream through the OTel collector as they run — one
  trace per run (root span holds verdict + headline; trace id stored on the
  diagnosis), one span per step with the exact SQL, the narrator call with token
  usage — and the seeded "RCA Overview" dashboard reads the same rollup the
  investigator queries. Traces land in ClickHouse too: the audit log is queryable
  in the same engine as the data it audits.

## LLM provider selection & rationale

Because the LLM only narrates, the model can be small: default **OpenAI
`gpt-5-nano` with `reasoning_effort: minimal`** — the narrator copies figures out of
a finished bundle, so reasoning tokens buy nothing. The narrator is provider-agnostic
(Anthropic / Google via the same zero-dependency HTTP client) with a deterministic
**template mode** requiring no key at all — the pipeline's correctness never depends
on any LLM being up, funded, or honest, because the guardrail assumes none of the
three.

## Scale & generality

A metric here is a (numerator, denominator) pair over dimensioned events — new
domains (sign-ups, error rates) are whitelist rows, not redesigns. The rollup is
SummingMergeTree: detection cost scales with series × hours, not events. The unseen
slice loaded and diagnosed with **zero code changes** — the release-day requirement
this design was built around.
