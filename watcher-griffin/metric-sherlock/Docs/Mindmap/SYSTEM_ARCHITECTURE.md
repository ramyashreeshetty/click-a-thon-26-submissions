# System Architecture

Raw Events -> ClickHouse -> Materialized Rollups -> Investigation Engine -> Evidence Generator -> LLM Narrator (Observed by Langfuse) -> API/UI

## Responsibilities
- ClickHouse: storage, aggregation, localization. Two isolated databases with the same schema — `ad_events_main` (primary, 9M events) and `unseen_data` (the sealed 1.5M-event incident drop) — selected per request/CLI by the dataset registry (`engine/datasets.py`). Each holds the star schema, 3 dictionaries, 19 rollups (12 `hourly_*` + 7 monitoring), the monitoring state tables (`baselines`/`metric_events`/`incidents`/`sweep_runs`/`sweep_coverage`), and the `investigations`/`scan_ticks`/`investigation_chat` app-state tables.
- Monitoring layer (`engine/sweep.py` → `cluster.py` → `signature.py` → `impact.py`): 10 metrics × 16 scopes × 14 grains against robust bands (`bands.py`, thresholds backtested by `scripts/backtest.py`); breaches cluster into incidents with a named mechanism (S1–S11) and a signed $/day impact.
- Investigation Engine: orchestration and drill-down as a **LangGraph `StateGraph`** (`engine/graph.py`) over the deterministic steps (`baseline.py` → `decompose.py` → `rank.py` → `drilldown.py` → `rule_out.py` → `evidence.py`). Drill-down is genuinely **recursive** — a node looping back on itself up to `max_drilldown_depth`. Rollups queried first; raw `ad_events` only as a logged fallback. See `INVESTIGATION_ENGINE.md`.
- Langfuse: the chosen "meaningfully integrate ClickStack/Langfuse/LibreChat" integration. One parent span per investigation; every query is a **real-time** child span opened by `engine/ch_client.py` as it executes (true durations, true parallel overlap), the narrator call is a generation, and rule-outs are events. Gated so the scanner's routine ticks never spam it. See `engine/tracing.py`.
- LLM (`engine/narrator.py`, `engine/chat.py`): explanation only — restates numbers already in the evidence bundle and cites the `source_step` query each came from; never computes; degrades to an explicit "narration unavailable" state rather than fabricating.
- Scanner (`engine/scanner.py`): the detection loop, running as **its own compose service** — never a FastAPI background task, because the API is multi-worker and that duplicates every tick. Two instances run: `scanner` (primary) and `scanner-unseen` (`--dataset unseen`), one per database.
- API/UI: stateless FastAPI JSON API (`:8088`, per-request `?dataset=` binding echoed via `X-Dataset`) + a React/Vite UI behind nginx (`:8089`) with a dataset switcher. `./scripts/deploy.sh` starts all four services with preflight/postflight checks.
