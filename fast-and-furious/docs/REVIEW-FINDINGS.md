# Adversarial Design Review — Findings

*Four independent attack lenses over `DESIGN.md` (draft v1) + `EVIDENCE.md`, each major/critical finding independently verified by a refuter agent with access to the real data. Produced 2026-08-01, before design finalization. The finalized decisions in `DECISIONS.md` resolve or accept each item.*


## Lens: ClickHouse engine mechanics — DDL semantics and query patterns

### [CRITICAL] Bg-edge delta emission convention contradicts the ground-truth contract; ~9% error at the peak minute

**Scenario:** DESIGN.md §2.2 says AppBackgrounded 'deactivates immediately' (second grain), but Tier-2 deltas are emitted at minute grain, and the ground-truth CSV (EVIDENCE F14/I6) excludes a minute only if it is WHOLLY inside the bg window (b <= M AND f >= M+60). If the compactor closes the interval at floor(bg_ts) — the natural reading of 'immediate' at minute grain — every session with a bg edge in minute M loses M, which ground truth still counts. Measured on the real data: 266 sessions have an AppBackgrounded event inside the global peak minute 10:56 UTC (fg=2,970), and 238–317 in each of the top-5 peak minutes. The reported peak could come out ~9% low (or high, if closed at ceil while GT used floor of a different rule) versus the private ground truth — on the single most-judged number. EVIDENCE itself warns: 'must match those exact conventions or expect off-by-one-minute diffs'.

**Proposed fix:** Pin the delta-emission convention to the diff target explicitly: open delta at m0 of the first qualifying event, close delta at the first minute wholly contained in the bg window (i.e. -1 at ceil-to-minute of bg_ts, not floor), reactivate at m0 of fg. Add a compactor unit test that replays the full extract and diffs the serving cumsum against ground_truth_foreground_per_minute.csv expecting 0 differing rows before the unseen day arrives; keep 'immediate second-grain close' only as the parameterized knob, not the default.

*(claim checked empirically against the real data by the reviewer)*

### [CRITICAL] Timezone-naive toDate()/DateTime64 makes day partitions and day-anchored cumsum IST-based; silently breaks on the unseen day

**Scenario:** raw_events declares `event_date Date MATERIALIZED toDate(event_time)` and `event_time DateTime64(3)` with no timezone, so partitioning follows server timezone. This environment's ClickHouse/chdb session timezone is Asia/Kolkata (verified: an event at 2026-07-26 20:00:00 UTC materializes event_date = 2026-07-27). The current extract ends 11:30 UTC so nothing ever crosses the 18:30 UTC IST-midnight line and every test passes. When the unseen FULL day arrives, all events after 18:30 UTC (~23% of a uniform day) land in the wrong partition, the compactor's day-split and the Tier-2 `day` column inherit IST days, and day-anchored cumsum resets at IST midnight — so any benchmark query with UTC day semantics ('peak on <date>') reads the wrong window and returns wrong numbers, with no error raised. EVIDENCE already documents that IST rendering caused a cross-investigator discrepancy.

**Proposed fix:** Make time zone explicit everywhere: `event_time DateTime64(3,'UTC')`, `event_date MATERIALIZED toDate(event_time)` (now UTC via column tz), compactor day-split via toDate(ts,'UTC') and minute via toStartOfMinute(ts,'UTC'), and Tier-2 `minute DateTime('UTC')`. Add one assertion query to the unseen-day protocol: min/max(event_date) must equal min/max(toDate(event_time,'UTC')).

*(claim checked empirically against the real data by the reviewer)*

### [MAJOR] WITH FILL applied after the window cumsum zero-fills `concurrent`, corrupting the series and the judged avg

**Scenario:** §3.5 computes `sum(d) OVER (ORDER BY minute)` and says missing minutes are 'zero-filled via WITH FILL'. Window functions execute BEFORE the outer ORDER BY ... WITH FILL, so filled rows get the column default: verified with the exact query shape — a session open 10:00–10:05 renders concurrent = 1,0,0,0,0,0 instead of 1,1,1,1,1,0. Any range containing delta-free minutes (quiet days Jul 22–25, whole-day averages, off-peak hours) reports avg far too low and a sawtooth-to-zero series; conversely with NO fill, avg is computed only over delta-bearing minutes and is biased high. Peak (max) survives by luck; average — an explicitly judged output — does not.

**Proposed fix:** Move WITH FILL into the inner subquery so d=0 rows exist before the cumsum: `SELECT minute, sum(delta) AS d ... GROUP BY minute ORDER BY minute WITH FILL FROM toDateTime({d}) TO toDateTime({d})+86400 STEP 60`, then window over that (verified: yields 1,1,1,1,1,0). Alternatively keep the outer fill but add `INTERPOLATE (concurrent AS concurrent)` to carry the running value forward.

*(claim checked empirically against the real data by the reviewer)*

### [MAJOR] §3.7 live-count query reads raw AggregatingMergeTree rows without finalizing — multi-fold overcount across unmerged parts

**Scenario:** `SELECT count() FROM session_state WHERE last_activity_ts > now()-120s AND end_ts = 0-sentinel` treats each part-row as a session, but an active session under 30–60s insert batching has a partial-state row in EVERY recent unmerged part, and a session whose End arrived in a newer part still has older rows with end_ts = sentinel that pass the filter. Verified: 1 open + 1 ended session across 5 parts returns 4 (truth: 1); the ended session alone returns 2 (truth: 0). During the live replay demo — precisely when this number is on screen — the 'right now' count inflates by roughly the unmerged-part multiplicity and never excludes freshly-ended sessions. The same footgun applies to the compactor's read of Tier-1 state: it must finalize with GROUP BY + max()/-Merge combinators, not read part-rows.

**Proposed fix:** Finalize before filtering: `SELECT count() FROM (SELECT user_id, video_session_id FROM session_state GROUP BY user_id, video_session_id HAVING max(last_activity_ts) > now()-INTERVAL 120 SECOND AND max(end_ts) = toDateTime64(0,3))`. Document the rule 'never read session_state without GROUP BY session + -Merge/max' and apply it in the compactor's dirty-session select as well.

*(claim checked empirically against the real data by the reviewer)*

### [MAJOR] Compactor step 'clip at end_ts' with the 1970 sentinel erases every open session's intervals mid-replay

**Scenario:** The 0-sentinel is safe for merging (max(1970, real) = real — that half of the attack is refuted), but §3.4 step 2 says the compactor 'clips at end_ts' with no open-session guard. For any session whose End has not yet arrived, end_ts = 1970-01-01, so a naive `least(interval_end, end_ts)` clips every interval to nothing: during the live replay and during the unseen-day streaming ingest (the exact 'open sessions exist only mid-replay' regime of E9), all in-flight sessions emit zero intervals and the live concurrency curve reads ~0 until Ends arrive, then jumps. At-rest benchmarks on fully-closed data would pass, hiding the bug until the demo.

**Proposed fix:** Guard the sentinel explicitly in the compactor: `clip_ts = if(end_ts = toDateTime64(0,3), toDateTime64('2299-12-31',3), end_ts)` (or make end_ts Nullable-free by using a far-future sentinel with min semantics — but keep max + 0 and branch). Add a replay test asserting nonzero serving concurrency while >0 sessions are open.

### [MINOR] dictGet default ('') for unseen-day content_ids gets permanently baked into delta rows; LIFETIME refresh never re-dirties sessions

**Scenario:** video_type is denormalized into concurrency_deltas at compaction time via dictGet. If the unseen day contains content_ids absent from the currently-loaded dictionary (new catalog rows loaded after events, or within the 300–600s LIFETIME staleness window), plain dictGet returns the type default '' — not the normalized 'unknown' — and that value is frozen in the serving rows: a later dictionary refresh does not re-dirty sessions, so no correction deltas ever fix it. video_type-filtered benchmark queries then split one slice across ''/'unknown'/(eventual correct) values.

**Proposed fix:** In the unseen-day protocol, load/refresh the content dim and run `SYSTEM RELOAD DICTIONARY dict_content` BEFORE the first compactor pass over new data; use `dictGetOrDefault(dict_content,'video_type',content_id,'unknown')` everywhere; optionally have the compactor re-dirty sessions whose compacted video_type = 'unknown' after a dictionary reload.

### [MINOR] argMax ties at identical-millisecond timestamps make platform/content attribution nondeterministic across compactor runs

**Scenario:** E11/E20 show exact duplicate rows at identical ms timestamps and 95 sessions emitting under 2 platforms. `AggregateFunction(argMax, String, DateTime64(3))` breaks ties arbitrarily and the winner can change as parts merge in different orders — so a dual-platform session's attributed platform can flip between compactor runs even with no new data, emitting spurious correction-delta pairs that move the session between platform slices run-to-run (flickering slice numbers during the demo; churn rows in SummingMergeTree).

**Proposed fix:** Make the tiebreak deterministic: argMax over a tuple, e.g. `argMaxState(platform, (event_time, platform))` (or attribute via argMin of first non-Start event, per EVIDENCE §3), so re-merges and re-compactions are idempotent.


## Lens: Operational robustness + unseen-day protocol + hackathon-judging pragmatics

### [CRITICAL] Compactor has no atomicity or idempotent-replay story: crash/retry between the deltas insert and the emitted_intervals memo update silently corrupts concurrency, and 'No rebuild, ever' means there is no documented panic button

**Scenario:** §3.4 step 3 writes two tables per pass: INSERT correction deltas into concurrency_deltas AND update the ReplacingMergeTree memo emitted_intervals. ClickHouse cannot make two INSERTs atomic. Unseen-day load in the final hours, compactor pass dies (OOM, network blip, ctrl-C) after the deltas insert but before the memo write → operator re-runs it → the diff (new − old) is computed against the stale memo → the same correction deltas are emitted twice → SummingMergeTree happily sums them → every affected session is counted +1 (or −1, if memo-first ordering) at every minute of its interval, forever. With ~10.9K sessions all dirty at once after the bulk CSV insert (dirty_since = ingest wall-clock makes the ENTIRE day dirty in one pass), a single failed+retried first pass can shift the day's whole curve by hundreds of sessions — directly scored against private ground truth. Same failure via the watermark: 'dirty_since > last_watermark' with watermark = pass start time races inserts committing during the pass (worse on ClickHouse Cloud, where the compactor SELECT may hit a replica that hasn't seen the freshest parts under SharedMergeTree) → sessions skipped forever, silent undercount. And the design's proud 'No rebuild, ever' means when this happens at 11pm there is no recovery procedure written down.

**Proposed fix:** Three concrete changes: (1) Make deltas a derived artifact of exactly one INSERT: write only to emitted_intervals (row = session, new interval set, old interval set, version), and let an incremental MV on that insert explode the (new − old) correction deltas into concurrency_deltas — MV writes ride the same insert, so a retried pass recomputes diff-vs-updated-memo = 0 rows, i.e. idempotent by construction. Read the memo with FINAL or argMax-by-version, never raw (ReplacingMergeTree dedup is eventual). (2) Watermark with overlap: process dirty_since > last_watermark − 60s (idempotence makes reprocessing free), persist the watermark in a 1-row table, and on Cloud run the compactor SELECT with select_sequential_consistency=1. (3) Write the rebuild runbook anyway: TRUNCATE concurrency_deltas + emitted_intervals, reset watermark to 0, run one compactor pass — at 1x that is sub-second (E20), at 100x minutes. Rehearse it once before event day.

### [MAJOR] Live replay breaks the 'deltas bounded by sessions' claim: open intervals force ~2 correction rows per active session per compactor pass, and the demo curve wobbles at the leading edge

**Scenario:** The design never says how a still-open session (no End yet, last activity < T ago) is represented in concurrency_deltas. Any representation needs a tentative close edge (last_activity + T or similar). During event-time replay of the hot hour, every heartbeat re-dirties its session, so each 30s pass re-diffs every active session and moves its close edge forward: 2 correction rows per session per pass. Measured on the real data: avg 1,092 (max 2,359) sessions have qualifying activity per 30s window in the hot 90 minutes → ~262K correction rows/hour at 1x and ~26M/hour at 100x — delta-table write volume scales with EVENTS, not sessions, during live operation, directly contradicting §3.5's 'deltas/day ≈ 2 × intervals/day, bounded by sessions'. Reads of the current day inflate until background merges collapse the zero-sum pairs. Visually, the last ~2 minutes of the demo curve dip (tentative close) then recover (correction) every pass — judges watching a live curve see it flicker.

**Proposed fix:** Adopt a stable-region rule: the compactor only finalizes and emits interval edges strictly older than event_watermark − T (nothing about them can change except a late event, which the correction path already handles); serve the leading ≤3 minutes of the curve by UNIONing a direct scan of session_state (same shape as the §3.7 'right now' query, grouped per minute) on top of the deltas cumsum. State the resulting leading-edge staleness (compactor cadence + T) explicitly in the demo script.

*(claim checked empirically against the real data by the reviewer)*

### [MAJOR] §3.7 'right now' query is wrong twice: it reads AggregatingMergeTree partial rows without merging, and it compares event-time against wall-clock now() which is meaningless during replay

**Scenario:** (1) AggregatingMergeTree keeps multiple unmerged partial rows per (user_id, video_session_id) until background merges run — guaranteed during the hot hour when a session's state is touched by many insert blocks. 'SELECT count() FROM session_state WHERE last_activity_ts > now()−120s AND end_ts = 0' counts partial ROWS, not sessions: a session that already ended still has earlier partial rows with end_ts=0 and a recent last_activity_ts → overcount; conversely a session whose latest partial row lacks recent activity is dropped. The one number shown live to judges is wrong precisely when traffic is highest. (2) The dataset's event-times are 2026-07-26; the demo replays in event-time order days later, so now()−120s matches nothing and the query returns 0 — unless timestamps are shifted, which the design never specifies.

**Proposed fix:** Rewrite as SELECT count() FROM (SELECT max(last_activity_ts) la, max(end_ts) e FROM session_state GROUP BY user_id, video_session_id HAVING e = 0 AND la > {replay_clock} − 120) — and define the replay clock as max(event_time) ingested (one cheap query, or a variable the replayer maintains), not now(). Decide now whether the replayer shifts timestamps to wall-clock or keeps originals, and use the same clock everywhere.

### [MAJOR] Timezone is unpinned in every DDL: the chdb prototype runs in Asia/Kolkata, ClickHouse Cloud runs in UTC — day partitions, day-split anchors, and WHERE day={d} all silently shift by 5.5h on migration

**Scenario:** Verified: timezone() in the chdb prototype environment = Asia/Kolkata; ClickHouse Cloud services default to UTC. Every date derivation in the design inherits server TZ: raw_events.event_date MATERIALIZED toDate(event_time), the compactor's 'split at day boundaries', concurrency_deltas.day, and the day-anchored cumsum. On the tuning data 6,140 events across 34 sessions land on a different calendar date in IST vs UTC; if the unseen day's live event runs through 00:00 in either zone (an evening IST event crosses UTC midnight at 18:30 UTC... an event ending after 05:30 IST crosses IST midnight) whole swaths of intervals get split at different anchors than the prototype was validated on. Concretely: the team validates numbers in chdb (IST days), loads the same SQL on Cloud (UTC days), and 'WHERE day = 2026-07-27' now returns a different minute range — peak/avg answers change, and the EVIDENCE base itself records that IST-vs-UTC rendering already confused their own investigators once. Minute buckets are safe (IST offset is whole minutes) but day anchors are not, and the benchmark will quote one specific zone.

**Proposed fix:** Pin the zone in the schema, not the server: DateTime64(3,'UTC') for all timestamp columns, toDate(event_time) → toDate(event_time) over the UTC-typed column (or explicit toDate(x,'UTC')), DateTime('UTC') for delta minutes. Report benchmark answers as epoch-second minute starts plus a rendered UTC string, and state the convention in the submission. One sanity query in the runbook: compare min/max event_date on prototype vs Cloud after load.

*(claim checked empirically against the real data by the reviewer)*

### [MAJOR] Unseen-day content_ids missing from the content dictionary: dictGet returns '' (not 'unknown'), so a video_type or title filter on the day's new content returns zero rows

**Scenario:** The 100% join coverage (E13) was measured on the tuning extract; the unseen day is a NEW day of a streaming service — its headline live event or new releases plausibly have content_ids absent from the static 33,464-row content.parquet. dictGet on a missing key returns the type default '', not the normalized 'unknown' (only the dim table's own empty strings were normalized). The compactor then stamps serving rows with video_type='' and title='': a benchmark query 'peak concurrency for live content on the unseen day' filtered video_type='live' (or ='unknown') misses the biggest content of the day entirely and returns a drastically wrong peak; GROUP BY video_type splits ''/'unknown' into two buckets. Nobody notices, because the global numbers still add up.

**Proposed fix:** Use dictGetOrDefault(dict_content, 'video_type', content_id, 'unknown') (same for title/category) everywhere; add a runbook step for the unseen day: count distinct event content_ids missing from the dictionary (one query), and if a refreshed content file arrives, insert it and SYSTEM RELOAD DICTIONARY before the compactor drain. Also persist raw content_id in the deltas (already done) so enrichment can be re-derived at query time if the dictionary is fixed late.

### [MAJOR] §5 're-verify with one profiling query' names no query, no decision rule, and no mechanism to recompact if T must change

**Scenario:** The unseen day lands at 10pm; the profiling step is a single unnamed query with no threshold for action. If the new day's cadence differs (the vendor's own data dictionary claims 60s — the tuning data's 40s could be one client version's behavior), the team has minutes to (a) decide which statistic to trust, (b) pick a new T, and (c) discover that nothing in the pipeline can re-emit intervals under a new T: dirty_since is max(ingest wall-clock), already older than the watermark after the first drain, so changed policy knobs (§7) silently apply only to future events. Mitigating fact worth stating in the defense: at minute grain the coverage rule {m0, m0+60, m0+120} tolerates gaps up to ~180s before a minute goes uncovered, so a 60s cadence survives single missed pings with T=120s — the real exposure is cadence ≥90s or a new platform emitting only lifecycle events.

**Proposed fix:** Write the exact protocol into §5: (1) the query — per-session gap distribution of the trio bundle AND of any-event gaps, per platform, on the new day (the F8/F5 SQL, kept as a script); (2) the rule — T = max(120s, 3 × round(p50_trio_gap)) rounded up to a 60s multiple; escalate only if p50 cadence > 60s or a platform has >20% zero-trio sessions with no other mid-session events; (3) the mechanism — 'reset last_watermark to 0 and rerun the compactor' recompacts everything idempotently in seconds at 1x (needs finding #1's idempotence fix); rehearse it. Also record the observed cadence in the submission as evidence of the re-verification the judges are told about.

### [MAJOR] Benchmark-shape insurance is cheap and missing: 'concurrent users' vs sessions diverges 3.3% at peak (bot alone = 84 sessions), and app_version/audio_language filters are unanswerable from the serving layer

**Scenario:** The benchmark queries are unknown until event day, and the serving layer fixes dims = {platform, content_id, video_type}. Measured on the real data at the foreground peak minute (10:56 UTC): 3,463 covered sessions vs 3,348 distinct users — a 115-count (3.3%) gap, 84 of it from the known bot user's simultaneous sessions. If the benchmark says 'concurrent viewers/users', the delta model (which can only add sessions) is systematically high and cannot be patched at query time. Similarly 'peak concurrency on app_version 6.34.8' or 'audio_language=hin' cannot be answered from deltas at all — only a raw-table brute force, exactly the anti-pattern the design's own E20 says judges will penalize on read volume. Note title/category/video_type substring filters are FINE (all functions of content_id, resolvable via dictGet over the 4.3K grid) — the gaps are user-grain and the two non-content dims.

**Proposed fix:** Three cheap additions now: (1) extend the §3.6 comparison path with a second per-minute state uniqCombinedState(user_id) keyed (minute, platform) — answers user-grain concurrency approximately and doubles as the bot-exclusion story; (2) add app_version to the delta dims — measured grid grows only 4,349 → 5,051 combos (+16%), and it is per-session-constant (F18: varies in 0 sessions) so attribution is exact; remember to add it to the SummingMergeTree ORDER BY, or merges will pick arbitrary values; (3) for audio_language (grid → 10,072, still tiny, but 16.1% of sessions genuinely switch mid-session) either emit per-interval argMax attribution with a documented divergence bound, or explicitly pre-write the defense: 'per-event language attribution requires interval re-splitting; we chose X'. Doing (2)+(3) costs one compactor column each today and is impossible to retrofit during the event.

### [MINOR] Liveness qualifying set is a hardcoded event_type whitelist — a new event_type on the unseen day silently punches holes in sessions

**Scenario:** §2.1 justifies 'any event of the session' (E2) but implements it as event_type IN (VideoSessionStart, VideoPlay, VideoHeartbeat, AppForegrounded). The taxonomy is already known to be unreliable (E3: event_type is 'a lie'). If the unseen day's client version introduces e.g. event_type='VideoPause' or 'AdBreak' as proper types (plausible — pause/resume being mistyped today looks like a bug someone fixes), sessions whose mid-stream telemetry arrives under the new type show ≥120s 'silent' gaps → false cuts → undercounted concurrency on exactly the cohort that changed.

**Proposed fix:** Invert to a blacklist: qualifying = event_type NOT IN ('AppBackgrounded', 'VideoSessionEnd') (decide VideoError explicitly; it never terminates per F21). Unknown future types then default to keeping a session alive — the safe failure mode — and the change is one line in the ingest MV today.

### [MINOR] chdb→Cloud porting leftovers: refreshable MVs never fire in the chdb prototype, and query_log evidence on Cloud must be read via clusterAllReplicas

**Scenario:** (1) §3.4 offers 'refreshable-MV / cron' — in a short-lived chdb process refreshable MVs never execute, so the prototype exercises only the cron path; if the team flips to REFRESH EVERY on Cloud in the final hours, the compactor's SQL runs under different settings/session context than everything validated (and refresh failure modes — skipped rounds under load — were never rehearsed). (2) The §5 evidence step reads system.query_log; on Cloud that table is per-replica, so the benchmark queries' rows_read/latency evidence silently misses queries routed to other replicas — an evidence extract showing half the queries looks sloppy exactly where judges are told to look.

**Proposed fix:** Pick ONE compactor trigger (external cron/scheduler driving the same INSERT…SELECT) and use it in both environments. For evidence, query clusterAllReplicas('default', system.query_log) filtered on a query_comment tag you attach to every benchmark query (SETTINGS log_comment='bench_q3'), which also makes the extract self-labeling.


## Lens: Scale, latency, and the judges' "what do your queries read" criterion

### [CRITICAL] §3.7 live 'right now' query is wrong three ways: counts unmerged partial states, misses Ends in unmerged parts, and ignores the foreground gate (+10.1% measured at peak)

**Scenario:** session_state is AggregatingMergeTree; states merge only during background merges. During the hot hour a 12-min session's rows span many unmerged parts, so `SELECT count() ... WHERE last_activity_ts > now()-120s AND end_ts = 0` (no GROUP BY, no -Merge) counts each session once per recent unmerged fragment — in a 3-parts-per-session simulation at 100x scale (3.27M rows) the as-written query returned 436,169 vs the correct 157,805 (2.8x inflation, nondeterministic with merge timing). Independently, a fragment written before the End event arrives has end_ts=0, so finalized sessions still count. Third: the query has no bg gate — on the real data at the fg peak instant (10:56 UTC), 'qualifying event in last 120s AND no End' = 2,874 sessions vs 2,610 after excluding currently-backgrounded sessions: a 10.1% overcount, i.e. the marquee live demo number reintroduces exactly the naive-overcount error the whole design exists to kill (E7).

**Proposed fix:** Rewrite as GROUP BY (user_id, video_session_id) with merge semantics: `HAVING max(end_ts)=0 AND max(last_activity_ts)>now()-120` plus a bg gate `AND NOT (max(bg_ts) > greatest(max(fg_ts), max(last_activity_ts)))` — needs last-bg/last-fg as SimpleAggregateFunction(max) scalar columns in session_state (add them; the groupUniqArray arrays are not cheaply usable here). Measured cost of the grouped query at 100x (3.27M rows): 84 ms on a laptop — the correct version is affordable, so there is no excuse for the fast-but-wrong one.

*(claim checked empirically against the real data by the reviewer)*

### [CRITICAL] Compactor delta-emit and emitted_intervals memo update are not atomic and runs are not mutually excluded — double-emitted corrections permanently corrupt SummingMergeTree counts

**Scenario:** §3.4 step 3 does two separate INSERTs per tick: correction deltas into concurrency_deltas (+ rollups) and new intervals into the emitted_intervals memo. Two failure paths: (a) crash/retry between the two inserts → next tick diffs against a stale memo and re-emits the same corrections; (b) the 30–60s cron: at 100x the peak tick rebuilds ~295K sessions (2,948 measured at 1x/60s tick) plus a ReplacingMergeTree FINAL memo read — if a run overruns its interval, the next run reads the same memo state and both emit the same deltas. SummingMergeTree just adds; duplicated +1/−1 corrections don't cancel (they're identical pairs, doubling the net change), so the served concurrency drifts from ground truth silently and unrecoverably without a rebuild — failing the correctness-vs-private-ground-truth criterion under exactly the hot-hour load the benchmark applies.

**Proposed fix:** Make emission idempotent and single-flight: (1) mutual exclusion — use a refreshable materialized view (refreshes never overlap themselves) or an explicit lock row, never bare cron; (2) atomicity — insert only into emitted_intervals tagged with a run_id, and derive concurrency_deltas via an MV on emitted_intervals inserts that computes (new − old) in the same statement, so deltas and memo advance in one atomic insert; or keep the two-insert design but key deltas by (session, run_id) into a Replacing/Collapsing staging layer so a replayed run deduplicates.

### [MAJOR] The compactor is a rolling full recompute of the active set, not incremental: 73.3% of rebuilds are pure heartbeat tail-extensions, total work ≈ 3.7× a one-shot brute-force rebuild, and correction churn is ~7× the final delta volume

**Scenario:** Measured on the real data (hot window 09:00–11:30 UTC, 60s ticks): peak tick has 2,948 dirty sessions, 127,047 session-rebuilds total (200,469 at 30s ticks) — every active session is re-dirtied every tick by its 40s heartbeat and fully rebuilt ~12–24 times over its life. Each rebuild re-reads the session's whole groupUniqArray state: 36,324 minute-entries at the peak tick, 1.45M over the window — 3.7× the ~386K (session,minute) pairs of one brute-force pass (E20), so 'incremental' does MORE total work than the rebuild it brags about avoiding, plus a per-tick FINAL diff against a memo that itself accrues 12–24 versions per session. Worse for the judges' read criterion: every open session's provisional close edge (last_activity+T) moves every tick, forcing a 2-row correction pair per session per tick — 73.3% of rebuilds (93,116 of 127,047) have NO real bg/fg/end edge at all. That's ~254K–400K correction rows at 1x over 2.5h vs ~60K final at-rest deltas (~30K intervals × 2); at 100x with 30s ticks, ~40M correction rows/day into the hot day partition, ×3 with the two rollup MVs — versus the design's stated '~50× smaller than the raw stream, bounded by sessions'. §3.4's 'No rebuild, ever' and §3.5's read claim are both falsifiable by a judge running one query mid-replay. (Measured mitigation: even 40M unmerged delta rows GROUP BY minute answered in <10ms in chdb, so latency survives — the claims don't.)

**Proposed fix:** Split hot/cold: the compactor emits deltas only for CLOSED interval edges (bg observed, End observed, or last_activity older than T+slack) — each interval is emitted once, cutting rebuilds/emissions to real edges (~34K vs 127K in the window) and delta volume to the at-rest ~2×intervals figure. Serve the open-session live tail (last ≤120s) directly from session_state (the corrected §3.7 query, 84ms at 100x) and UNION it with the Tier-2 cumsum at query time. Accept eventual consistency of ≤1 tick for open sessions; the served number is actually FRESHER because closes no longer wait for the next compaction.

*(claim checked empirically against the real data by the reviewer)*

### [MINOR] session_state has no partition/TTL and its scan is unprunable — every 30–60s compactor tick and every live query scans all sessions ever ingested, not the active set

**Scenario:** session_state is ORDER BY (user_id, video_session_id) with no PARTITION BY and no TTL; both `dirty_since > watermark` (compactor step 1) and `last_activity_ts > now()-120s` (§3.7) are non-key filters, so every tick is a full-table scan-and-group. ## Lens: Correctness of the active-interval semantics vs the ground-truth contract

### [CRITICAL] Interval-to-minute conversion is unspecified, and both natural delta-emission conventions fail against the ground truth (-5.9% or +3.6% at peak)

**Scenario:** The compactor (§3.4) does continuous-time interval arithmetic (merge runs, subtract bg windows, clip at end_ts) and 'emits +1/-1 deltas at interval edges' at minute grain, but never states how a sub-minute edge maps to a minute. Ground truth is a per-minute set semantics: a qualifying event at t covers {m0, m0+1, m0+2}; bg excludes only wholly-contained minutes. Convention 1 (truncate: -1 at toStartOfMinute(interval_end)): the session's final minute is dropped — GT counts the End minute for 10,778 of 10,866 sessions (99.2%), and 175 GT-active sessions have their End inside the peak minute, so the served peak reads 2,795 vs 2,970 (-5.9%); every bg edge minute is dropped the same way (14,700 more edges). Convention 2 (any-overlap / round outward): 6,287 bg->fg windows open AND close within a single minute (5,302 sessions, all in GT-active minutes, 107 at the peak minute) — the split interval produces two fragments overlapping the same minute, the summed deltas count the session twice, and the peak reads +107 (+3.6%). Concrete micro-case: activity at 10:00:10 then bg at 10:00:20 — GT counts minute 10:00 (bg at :20 does not wholly contain it); truncation emits +1@10:00 and -1@10:00 which cancel, so the design counts nothing. bg 10:00:30 / fg 10:03:30: GT excludes exactly {10:01, 10:02}; minute-start-containment conventions also wrongly drop 10:03. Interval [10:00:30, 10:05:10): GT-equivalent counts 10:05; truncation does not. The zombie-cap wording ('silent periods contribute at most T=120s') contradicts the coverage contract too: coverage always extends to m0+2 of the last event, i.e. up to ~180s of wall clock past it (an interval ending at last_ts+120s truncated to minutes systematically loses minute m_last+2).

**Proposed fix:** Drop continuous-time interval arithmetic in the compactor. ### Verdict 6: CONFIRMED (severity adjusted: critical)

I attempted to refute the claim on four fronts and failed on all of them; the claim stands, and the real data makes the blast radius WORSE than stated.

(1) Atomicity: §3.4 step 3 genuinely requires two writes per pass — INSERT correction deltas into concurrency_deltas AND upsert the emitted_intervals memo. Mitigating factors considered and rejected as refutations: the fault window per pass is small (but the pass count is large and the unseen-day bulk load at deadline is exactly when ctrl-C/OOM/re-run happens); the §3.6 cross-check exists (but only detects gross doubling, not partial duplication). ### Verdict 12: CONFIRMED (severity adjusted: critical)

The claim survives every refutation attempt. (1) Non-atomicity is real: §3.4 requires two writes per tick (correction deltas into concurrency_deltas, new intervals into the emitted_intervals memo); ClickHouse has no cross-table transactions, so a crash/retry between them either re-emits deltas against a stale memo (deltas-first ordering) or silently drops intervals (memo-first) — both permanent in SummingMergeTree. (2) Duplicated corrections do not cancel: (new − old) pairs re-emitted are identical, doubling the net change; SummingMergeTree just adds. (3) The design's 'refreshable-MV' hedge does not supply mutual exclusion: a refreshable MV writes exactly one target table, so the two-table compactor cannot be one refreshable MV — it is either two independently-refreshing MVs (race between them) or bare cron (no overlap protection). (4) The overlap load figure is verified against the real data: max 2,948 distinct dirty sessions per 60s tick at 1x peak (measured with chdb) → ~295K per-session rebuilds per tick at the 100x scale the design's own §5/E17 commits to, plus a FINAL scan of a ~1.09M-row ReplacingMergeTree memo under ~21.7K ev/s concurrent ingest — plausibly exceeding a 30–60s cron interval. (5) Insert dedup doesn't rescue retries: off by default on non-replicated MergeTree, and any newly arrived event changes the recomputed block checksum. (6) Severity is worse than 'recoverable': a duplicated correction set sums to zero over the day, so the natural invariant check (per-day sum(delta)=0) passes on corrupted data — the drift is invisible to cheap checks and fixable only by the full rebuild the design forswears ('No rebuild, ever'; §5's 'idempotent' claim is false as written). Trigger requires a fault or 100x overlap rather than the happy path, but the consequence is silent permanent corruption of the primary judged metric (correctness vs private ground truth), justifying critical.

**Improved fix:** Collapse the compactor to exactly one client INSERT and make replays idempotent by key: (1) Single-flight: run the tick as one refreshable materialized view (refreshes never self-overlap) whose target is emitted_intervals only; if cron is kept, take an explicit lock (Keeper lock or a claimed run-row checked at tick start). (2) Single-statement emission: the tick INSERTs only into emitted_intervals (each row tagged with session_key, interval_seq, and a monotonically increasing generation/run_id); a chained MV on emitted_intervals computes the correction deltas (new − previous generation) and pushes them into concurrency_deltas, so memo advance and delta emit share one insert's fate. Caveat the reviewer's fix misses: an MV joining its inserted block back against its own source table is only reliably consistent for single-block inserts — keep tick output in one block (it is only thousands of rows) and set materialized_views_ignore_errors=0 so an MV failure fails the whole insert, or precompute (new − old) in the tick's SELECT and carry both columns through one Null-engine staging insert with the two MVs hanging off it. (3) Idempotency backstop for retries: set a deterministic insert_deduplication_token per (watermark, run_id) so a blind re-run of the same tick is dropped by ClickHouse block dedup (enable non_replicated_deduplication_window on non-replicated tables); alternatively key the serving layer as ReplacingMergeTree ORDER BY (platform, content_id, minute, session_key, interval_seq, sign) with generation as version — replayed rows replace instead of add, and the serving query becomes GROUP BY minute SUM over argMax-latest rows with the same bounded read profile. (4) Do not rely on detection: duplicated correction pairs sum to zero per day, so no delta-sum invariant catches this — prevention is the only defense; state that explicitly in the trade-off table. Also fix §5's 'idempotent' wording to describe the mechanism above rather than asserting it.
