Base context audit

Overall conclusion: the context contains material stale, incorrect, and internally inconsistent content. It should not be treated as a single authoritative description of the current database.

Confirmed incorrect or stale claims

  • Forex table is stale or missing. The context describes forex_addon_events as an executed canonical table and includes it in the join map. The live inventory has no such table; querying it returns UNKNOWN_TABLE. Only the view forex_addon_application_funnel_finalized exists. Any raw-table analysis or schema claim for forex_addon_events is currently unsupported.
  • ETA field is wrong. application_started contains eta_shown Nullable(String), with values such as 24 hours, 3-5 days, 5-7 days, and 7-10 days. The claimed visa_issuance_eta_days Nullable(Int) column does not exist. Consequently, the literal on-time-delivery metric is not computable from this dataset.
  • Pre-application application_id claim is overstated. Empty application_id rates were 84.6% for destination_card_clicked, 84.6% for search_typed, and 84.5% for landing_page_scrolled—not 100%. Users can browse a second destination after already starting an application.
  • Conversion definition is self-contradictory. The context uses both “completed purchases / sessions” and “purchase_completed users / application_started users.” No session entity is available; app_session_id is an event attribute, not a validated session-count table. The application_started denominator is the implementable definition.
  • Funnel step numbering is inconsistent. The business overview lists a four-table spine ending at purchase_completed, while purchase_completed is described as funnel step 5 because pay_now_clicked is treated as a bridge. The stage labels should be standardized before reporting.
  • abandonment_recovery_events remains unsafe. The live table has 5,919 rows, but all rows have empty recovery_id and reminder_id; each event type reports only one distinct recovery/reminder key. This is consistent with the documented column-shift defect. The table must not be used for channel or reconversion rates, and its aggregate targets currently contain zero rows.

Validated context claims

  • The original funnel tables show the documented synthetic one-row-per-user pattern: application_started has 154,413 rows and users, document_uploaded 20,446, pay_now_clicked 14,739, and purchase_completed 7,054.
  • The envelope quirks are reproduced: duplicate_id is approximately 3%, backfilled rows approximately 2%, and Android-only OS nulls occur in the original funnel tables.
  • Timestamp ordering after document upload is unreliable. In the joined document→pay→purchase cohort of 7,054 applications, only 3,497 had pay after document, 3,673 had purchase after pay, and 3,648 had purchase after document. The order-agnostic application_id matching rule is therefore appropriate.

Known issue re-evaluation

  • K1 contradicted: iOS Gulf pay-to-purchase conversion was 64.6% versus 46.1% for non-Gulf iOS. This does not support a Gulf-iOS regression. The prior version-level analysis also found no dip across versions.
  • K2 confirmed: Android threshold crossing increased from 7.9% in Jan–Mar to 23.1% in Apr–Jun, while iOS was essentially flat at 8.5% to 8.9%. This confirms both the device skew and the claimed April timing in this dataset.
  • K3 untested: citizenship and retry_count have not been used to test the non-Latin MRZ hypothesis; no explicit MRZ-script field exists.
  • K4 partial: Schengen conversion declined from 4.84% in Jan–Mar to 4.52% in Apr–Jun, while other destinations declined from 4.73% to 4.42%. The direction is compatible with seasonal softness, but the similar non-Schengen movement prevents attributing the change specifically to slot scarcity.
  • K5 untested/blocked: WhatsApp values are present in the declared channel column, but the row-level key corruption makes the landed table unreliable. Do not report a WhatsApp effectiveness number.
  • K6 contradicted on timing: SUMMER20 redemptions were 59, 54, 64, 58, 61, and 37 from January through June, with no Q2 spike. There were also two July rows, so the documented campaign window should be clarified.
  • K7 contradicted: the five app versions remain approximately evenly represented each month, with no visible 7.45 rollout curve.

Recommended context corrections

  1. Remove or mark forex_addon_events as unavailable until the raw table is actually present; update the join map and forex metrics accordingly.
  2. Replace visa_issuance_eta_days with the actual bucketed eta_shown field and keep on-time delivery explicitly out of scope.
  3. Change “empty application_id” from absolute to approximate/conditional wording.
  4. Choose one conversion denominator and explicitly label session-based conversion as unavailable.
  5. Keep the timestamp-ordering warning and application_id matching rule.
  6. Retain the abandonment table as blocked until validated staging, correction, deduplication, replay, and reconciliation are complete.
  7. Upgrade K2 to confirmed, downgrade K4 to partial, and preserve K3 and K5 as untested.
